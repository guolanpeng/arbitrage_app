# Arbitrage application

Strategies, public market collection, account monitoring, and deployment live here.
Engine source remains in `D:/WorkSpace/arbitrage_platform`; the dashboard remains in
`D:/WorkSpace/market_dashboard`. Engine dependencies are managed by uv, not a custom
engine manifest or dependency resolver.

## Windows development

The local Windows CPython 3.13 wheel is in the ignored `engine-wheels/` directory.
It was repacked from the existing editable installation without compiling and is only
a local migration snapshot, not an approved Linux production release. On a new Windows
machine, put a compatible engine wheel in that directory first. uv is explicitly bound
to this local engine index, so it cannot substitute the public upstream package.

From the application root:

```powershell
uv sync --project python --frozen --group test --python 3.13.2
uv run --project python --frozen python -m pytest user_strategies examples/live/binance/portfolio_monitor scripts -q
uv run --project python --frozen --env-file .env python -m user_strategies.market_data
uv run --project python --frozen --env-file .env python examples/live/binance/portfolio_monitor/monitor.py
```

The existing local `.env` was copied during migration and is ignored by Git.
For a clean machine, copy `.env.example` to `.env` and configure it locally.
The monitoring launcher starts no trading strategy. Run
`scripts/start-monitoring.ps1 -ValidateOnly` to check settings without starting workers.
See [application documentation](user_strategies/README.md) for strategy commands.

## Engine versions and Linux deployment

The engine build stamps a unique PEP 440 package version, for example
`2.0.0rc6+build.123.attempt.1.g<FULL_ENGINE_COMMIT_SHA>`, before maturin builds the wheel.
After tests succeed, it publishes the wheel into the runner's flat wheel directory,
`/var/lib/arbitrage-engine/artifacts`. No new package server is needed.

Declare the engine base version in `python/pyproject.toml`. The `==2.0.0rc6` requirement
permits internal builds of that base release. At each application release, uv upgrades
only this dependency to the highest compatible published internal build and writes a
standard `uv.lock`. The exact internal version includes the full engine commit.

The Linux release project is generated from the same application dependencies, with a
Linux index and CPython 3.14 target. Other dependency versions use the existing lock as
preferences. The release includes its generated `uv.lock`, the selected wheel, and
hash-locked requirements generated by uv. Local flat-index entries in `uv.lock` have no
wheel hash, so deployment integrity is enforced by the hashed requirements instead.
Offline installation uses `--require-hashes`. Existing release archives and rollback
releases retain their own wheels and locks, regardless of later engine publications.

See [deployment guide](scripts/deploy/README.md) to configure runner access, the shared
wheel directory, and SSH secrets. Workflows are prepared locally; no remote configuration
or server services were changed by this code cleanup. Duplicate application sources and
deployment scripts have been removed from the engine checkout; develop application changes here.
